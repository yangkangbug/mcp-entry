# 产品方向与路线图

mcp-entry 的目标是通用、基于 MCP 标准的开源统一入口：让多个下游系统通过一致的工具发现、身份隔离和授权边界接入，而不是为某个客户端另造一套协议。

## 已实现：可验证的本地原型

- 官方 Go MCP SDK 与 Streamable HTTP。
- 配置驱动连接、标准 tools/list 分页发现、系统命名空间映射。
- 按用户隔离目录与下游凭证；列举和调用分别执行授权。
- 保留工具 schema 和元数据；对输入、目录规模和不支持的扩展设置明确边界。
- 模拟集成测试与 CI，覆盖异构工具、失败系统、恶意目录及有状态会话清理。

上述功能仍是虚构凭证、回环 HTTP 和内存状态的原型，不是可部署生产的完整认证网关。

## 接下来

1. 连接可靠性与可观测性：完善截止时间、取消、资源释放和脱敏错误，提供可复现的故障证据。
2. 契约回归与标准兼容性：以多种合规 MCP 服务验证发现、分页、schema 和调用语义；在明确资源边界与回归保障后，评估受限的本地 schema 引用支持。
3. 身份与凭证：先确定 OAuth/OIDC、账号绑定和租户信任模型，再实现安全存储、轮换和撤销。
4. 管理能力：在身份与权限边界稳定后，增加连接管理、策略更新和审计界面。
5. 真实系统接入：先验证只读场景；有副作用的操作需独立的授权、幂等和未知结果处理设计。

网关不解释业务参数中的 task_id、parent_task_id 等字段，不承担业务任务轮询、归属判定或业务幂等引擎；此类数据按工具契约不透明转发。

没有承诺上述里程碑的完成日期。新增功能必须说明适用范围、测试和安全边界，不以绕过标准或降低隔离为代价。

## 如何处理反馈

- 通用缺陷：可复现、影响标准行为或安全边界的错误，优先修复并加入回归测试。
- 配置问题：由地址、凭证、策略或部署配置导致的问题，通过清晰校验与文档解决，不写入客户端特判。
- 适配需求：确有普遍价值且不能由标准能力表达的差异，先评估明确、可选的适配边界，不污染核心协议。
- 暂缓需求：单一工作流特例、未证实的问题或超出当前安全范围的功能，先收集证据或记录，不直接扩展核心。

报告问题时请提供最小复现、版本、预期/实际结果及脱敏日志。不要提交真实 token、私人配置或客户数据。
